# Research Quality Contract

## 1. Scope / Trigger

Apply this contract when changing the single-platform Research Runtime,
research query generation, crawler result classification, Finding evidence,
or the existing Research Center task detail. The contract covers revision
`0012_research_quality_foundation` and later forward-compatible changes.

## 2. Signatures

### Database

`research_queries` is the durable query-gate record. Its required fields are
`research_task_id`, `query`, `normalized_query`, `query_type`, `platform`,
`source_type`, optional `source_content_id` / `source_finding_id` /
`parent_query_id`, `generation_reason`, deterministic scores, optional model
scores, `status`, `rejection_reason`, execution timestamps, and the counters
`result_count`, `new_content_count`, `existing_content_count`,
`updated_content_count`, and `duplicate_evidence_count`.

`evidence_occurrences` records discovery events independently from the
deduplicated `finding_contents` relation:

```text
research_task_id / finding_id / content_id / crawler_task_id /
research_query_id / first_seen_at / last_seen_at / occurrence_count
```

`finding_contents` carries `support_type`, `support_strength`, and
`support_explanation`; `findings` carries `counterevidence_status` and
`counterevidence_explanation`.

`crawler_tasks.research_new_content_count`,
`crawler_tasks.research_existing_content_count`, and
`crawler_tasks.research_updated_content_count` are the recovery checkpoint
written in the same transaction as successful library ingestion.

### Runtime/API

```python
evaluate_query(
    query: str,
    *,
    generation_reason: str | None,
    source_type: str,
    historical_queries: list[str],
    parent_query_id: str | None = None,
    source_content_id: str | None = None,
    source_finding_id: str | None = None,
) -> QueryQuality
```

The Research detail response exposes `queries`, deduplicated `findings`,
occurrence expansions, and result counters. The frontend validates these
fields with Zod before rendering them.

## 3. Contracts

### Query gate

Every candidate follows this order:

```text
normalize → classify/entity tokens → deterministic scores/history dedupe
→ one batch relevance call through ModelGateway → expected value
→ platform scope check → execute or persist rejection
```

Rules and model responsibilities are separate:

- specificity, novelty, noise risk, exact/approximate history dedupe, generic
  term rejection, source-chain completeness, and platform scope are
  deterministic backend behavior;
- relevance is scored in one bounded batch model call;
- expected value is calculated as
  `relevance * specificity * novelty`, not generated by the model;
- a candidate is inserted before it is executed or rejected;
- a non-user-goal query requires `parent_query_id` and at least one source
  content or Finding ID;
- standalone `app`, `工具`, `话题`, `agent`, `api`, `人工智能`, `AI`, `软件`,
  and `产品` are rejected with a visible reason, while concrete combinations
  remain executable;
- the production ResearchToolService advertises `supports_quality_queries`
  and requires the private quality-gate query ID for `search_library` and
  `submit_crawl`; test doubles may explicitly use the legacy path.

### Content classification

`LibraryRepository.ingest_task()` is the sole source of truth for result
classification by `(platform, source_content_id)`:

- `new_content`: no standard content row existed before the upsert;
- `existing_content`: the row existed and title, description, and author did
  not materially change;
- `updated_content`: an existing row changed in title, description, or author;
- interaction metric changes only create an `EngagementSnapshot` and do not
  increment `updated_content_count`;
- duplicate evidence is calculated from repeated standard content IDs across
  research queries, research tasks, or result records and never increases the
  independent evidence count.

The ingestion transaction writes the three research counters to
`crawler_tasks` before the Worker calls `record_crawl_completion()`. Runtime
or Worker recovery must read those checkpoint fields rather than assuming
zero.

### Evidence and Finding support

`finding_contents` is one row per Finding/content pair. `evidence_occurrences`
is an append/merge discovery log and may contain multiple query/crawler rows
for the same content. Finding APIs return one evidence item per normalized
`content_id` and expand its occurrences.

- facts require at least one `direct` link;
- inferences require a non-empty derivation and an explicit counterevidence
  status; `unknown` is not accepted for an inference;
- `found` counterevidence requires a `contradictory` evidence link;
- every evidence link has a support type, strength, and one-sentence
  explanation;
- legacy rows are displayed as `background` / `weak` with an explicit
  historical explanation rather than pretending old metadata existed.

All AI conclusions remain evidence-bound. Proposed user actions remain in the
existing owner approval queue and are never executed by the runtime.

## 4. Validation & Error Matrix

| Condition | Required behavior |
|---|---|
| Blank/too-short query | Persist `rejected` with a reason; do not execute |
| Missing `generation_reason` | Persist `rejected`; do not silently drop |
| Later query without parent and source | Persist `rejected` |
| Generic-only query | Persist `rejected` with the generic-term reason |
| Historical exact/near duplicate | Persist `rejected` with duplicate reason |
| Batch relevance parse failure | Reject every batch candidate; no crawl |
| Relevance/value below threshold | Persist score and rejection reason; no crawl |
| Requested crawl count outside 10–15 | Return a tool conflict; no crawler row is submitted |
| Fact without direct support | Reject `save_finding` |
| Inference without derivation/counterevidence state | Reject `save_finding` |
| Found counterevidence without contradictory link | Reject `save_finding` |
| Worker/runtime restart after ingestion | Recover persisted new/existing/updated counts |
| Existing pre-quality Research task | Show it with empty query/occurrence extensions and historical support metadata |
| Migration downgrade with quality rows | Refuse to discard quality data |

## 5. Good / Base / Bad Cases

- Good: `WorkBuddy 使用体验` is linked to a parent query and a concrete
  library content ID, receives one batch relevance score, and its crawl result
  updates the same query row with real four-way counts.
- Base: an old 8B task has no `research_queries`; the page says that the query
  trajectory is unavailable and labels legacy evidence metadata explicitly.
- Bad: the model emits `agent`, the Worker executes it without a query row, or
  a restart turns a previously ingested batch into `new_content_count = 0`.
- Bad: two query hits for one normalized content become two independent
  Finding evidence items.

## 6. Tests Required

- Query unit tests assert normalization, generic rejection, source-chain
  rejection, exact/near history dedupe, deterministic scores, and bounded
  batch relevance parsing.
- Repository tests assert direct-support facts, inference derivation and
  counterevidence constraints, occurrence merging, and independent-evidence
  deduplication.
- Library/Worker tests assert metric-only updates are not `updated_content` and
  that the ingestion transaction persists the three recovery counters.
- Runtime restart tests set persisted crawler counters and assert recovery
  preserves them.
- Alembic tests cover blank initialization, `0011 → 0012` populated upgrade,
  existing research associations, and `PRAGMA integrity_check = ok`.
- API/frontend tests assert Zod parsing, query/rejection visibility, four-way
  counts, occurrence expansion, support labels, sanitized summaries, and a
  390px layout.
- Before release run backend pytest with coverage `>= 86%`, frontend lint/test/
  build, and server-script syntax/tests.

## 7. Wrong vs Correct

### Wrong

```python
# The crawler succeeded, but recovery guesses instead of reading the commit.
research.record_crawl_completion(crawler_id, succeeded=True, new_content_count=0)
```

### Correct

```python
research.record_crawl_completion(
    crawler_id,
    succeeded=True,
    new_content_count=int(row["research_new_content_count"] or 0),
    existing_content_count=int(row["research_existing_content_count"] or 0),
    updated_content_count=int(row["research_updated_content_count"] or 0),
    result_count=int(row["actual_count"] or 0),
)
```
